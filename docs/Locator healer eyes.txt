## 3. Observation layer: what the agent should capture

For every failed locator or every visual reasoning step, capture this complete page state:

```json
{
  "url": "https://app/login",
  "title": "Login",
  "viewport": {
    "width": 1366,
    "height": 768,
    "devicePixelRatio": 1,
    "scrollX": 0,
    "scrollY": 320
  },
  "screenshot": "base64-image-or-file-path",
  "ocrBlocks": [],
  "domElements": [],
  "accessibilityNodes": [],
  "oldLocatorMetadata": {},
  "actionIntent": {}
}
```

For screenshots and OCR, Tesseract can produce TSV output containing fields such as `left`, `top`, `width`, `height`, `conf`, and `text`, which is useful for text bounding boxes. ([Tesseract OCR][1])

For DOM capture, Chrome DevTools Protocol `DOMSnapshot.captureSnapshot` can return a flattened DOM tree together with layout and selected computed style information, and can include DOM rectangles. ([Chrome DevTools][2])

For Playwright, locators are central to auto-waiting and retry behavior, and Playwright recommends user-facing locators such as role, text, label, placeholder, alt text, title, and test id. ([Playwright][3])

## 4. OCR layer: use OCR as visual hint, not truth

OCR output should be normalized into this format:

```json
{
  "text": "Submit",
  "normalizedText": "submit",
  "bbox": {
    "x": 820,
    "y": 540,
    "w": 90,
    "h": 36
  },
  "confidence": 0.96,
  "lineId": "line-12",
  "source": "tesseract"
}
```

OCR should answer:

```text
What text is visible?
Where is it visible?
How confident is the OCR?
```

OCR should **not** answer:

```text
Which XPath should I click?
```

Because OCR can see the word “Submit”, but the real clickable element may be the parent `<button>`, not the inner `<span>`.

## 5. DOM/layout layer: capture real clickable elements

Capture all visible and potentially interactable elements:

```javascript
const elements = [...document.querySelectorAll("body *")]
  .filter(el => {
    const r = el.getBoundingClientRect();
    const style = window.getComputedStyle(el);

    return (
      r.width > 0 &&
      r.height > 0 &&
      style.visibility !== "hidden" &&
      style.display !== "none" &&
      style.opacity !== "0"
    );
  })
  .map((el, index) => {
    const r = el.getBoundingClientRect();

    return {
      candidateId: "dom-" + index,
      tag: el.tagName.toLowerCase(),
      text: el.innerText?.trim() || "",
      directText: [...el.childNodes]
        .filter(n => n.nodeType === Node.TEXT_NODE)
        .map(n => n.textContent.trim())
        .join(" "),
      role: el.getAttribute("role"),
      ariaLabel: el.getAttribute("aria-label"),
      id: el.id,
      name: el.getAttribute("name"),
      type: el.getAttribute("type"),
      placeholder: el.getAttribute("placeholder"),
      title: el.getAttribute("title"),
      dataTestId: el.getAttribute("data-testid"),
      dataQa: el.getAttribute("data-qa"),
      className: String(el.className || ""),
      href: el.getAttribute("href"),
      disabled: el.disabled || el.getAttribute("aria-disabled") === "true",
      pointerEvents: style.pointerEvents,
      cursor: style.cursor,
      bbox: {
        x: r.x,
        y: r.y,
        w: r.width,
        h: r.height
      },
      cssPath: buildCssPath(el),
      xpath: buildXPath(el),
      clickable: isProbablyClickable(el)
    };
  });
```

Clickable detection should include:

```text
button
input
textarea
select
a[href]
[role='button']
[role='link']
[onclick]
elements with pointer cursor
custom components with click listeners
```

## 6. Accessibility layer: the semantic truth

Accessibility tree is very important because it tells you what the element means from a user perspective:

```json
{
  "role": "button",
  "name": "Sign in",
  "disabled": false,
  "checked": null,
  "expanded": null,
  "bbox": {}
}
```

For Playwright, prefer:

```javascript
page.getByRole('button', { name: 'Sign in' })
page.getByLabel('Username')
page.getByPlaceholder('Enter username')
page.getByText('Submit')
page.getByTestId('submit-button')
```

Playwright’s docs say `getByRole()` reflects how users and assistive technologies perceive the page, and when using role, you should usually pass the accessible name to pinpoint the exact element. ([Playwright][3])

This is stronger than raw XPath because it aligns with how the page is actually presented to users.

## 8. OCR-to-DOM matching algorithm

For every OCR text box, compare it with visible DOM elements.

Example:

```json
{
  "ocrText": "Continue",
  "ocrBox": { "x": 710, "y": 520, "w": 110, "h": 36 }
}
```

DOM candidates:

```json
[
  {
    "tag": "button",
    "text": "Continue",
    "bbox": { "x": 700, "y": 515, "w": 130, "h": 44 },
    "role": "button",
    "clickable": true
  },
  {
    "tag": "span",
    "text": "Continue",
    "bbox": { "x": 735, "y": 527, "w": 70, "h": 18 },
    "role": null,
    "clickable": false
  }
]
```

The healer should select the `<button>`, not the `<span>`.

### OCR-to-DOM matching score

Use this:

```text
OCR_DOM_SCORE =
  0.30 * text_similarity
+ 0.25 * bbox_overlap
+ 0.15 * center_distance_score
+ 0.15 * semantic_role_score
+ 0.10 * interactability_score
+ 0.05 * parent_clickability_score
```

Where:

```text
text_similarity:
OCR text vs innerText / aria-label / placeholder / title / accessible name

bbox_overlap:
Intersection-over-union between OCR box and DOM box

center_distance_score:
How close OCR center is to DOM element center

semantic_role_score:
button/input/link/select/textarea > div/span

interactability_score:
visible + enabled + pointer-events not none

parent_clickability_score:
if OCR matched child span, can parent button/a/div[role=button] be used?
```

## 9. Final candidate scoring model

After candidates are discovered from DOM, accessibility, OCR, and history, rank them using a final score:

```text
FINAL_CANDIDATE_SCORE =
  0.20 * intent_text_similarity
+ 0.15 * visual_alignment_score
+ 0.15 * accessibility_score
+ 0.15 * dom_structure_score
+ 0.10 * interactability_score
+ 0.10 * locator_stability_score
+ 0.10 * historical_similarity_score
+ 0.05 * uniqueness_score
```

### Meaning of each score

| Score                         | Meaning                                                     |
| ----------------------------- | ----------------------------------------------------------- |
| `intent_text_similarity`      | Does text/aria/label/placeholder match the intended action? |
| `visual_alignment_score`      | Does the element visually appear where expected?            |
| `accessibility_score`         | Does role/name match the action?                            |
| `dom_structure_score`         | Is it in the expected form/card/container?                  |
| `interactability_score`       | Is it visible, enabled, clickable?                          |
| `locator_stability_score`     | Can we build a stable locator?                              |
| `historical_similarity_score` | Is it similar to the old successful element?                |
| `uniqueness_score`            | Does the locator identify exactly one element?              |

For your XPath healer, I would keep the threshold like this:

```text
score >= 0.85:
    auto-heal and continue test

0.70 <= score < 0.85:
    heal only if validation passes strongly

0.55 <= score < 0.70:
    ask optional LLM/VLM to reason or mark as low-confidence

score < 0.55:
    fail with diagnostic report
```

## 11. Browser validation: final judge

Before accepting a healed locator, validate it.

```text
1. Does locator match exactly one element?
2. Is element attached to DOM?
3. Is it visible?
4. Is it enabled?
5. Is it inside the expected container?
6. Is it not covered by overlay?
7. Does it receive pointer events?
8. Does its accessible role/name make sense?
9. Does action produce expected result?
```

For Playwright, assertion APIs can validate locator state and result state, such as checking whether expected text appears after an action. ([Playwright][4])

For Selenium, validation can include:

```java
element.isDisplayed()
element.isEnabled()
element.getRect()
JavascriptExecutor elementFromPoint check
ExpectedConditions.elementToBeClickable()
```

Useful JS check:

```javascript
function receivesClick(el) {
  const r = el.getBoundingClientRect();
  const x = r.left + r.width / 2;
  const y = r.top + r.height / 2;
  const top = document.elementFromPoint(x, y);
  return el === top || el.contains(top);
}
```

This catches overlay/intercepted-click problems.

## 12. Final action execution strategy

Execution should follow this order:

```text
1. Native locator click/type/select
2. Scroll into view
3. Retry native action
4. Actions class / Playwright mouse action
5. JavaScript click only when safe
6. Coordinate click only as last fallback
7. Re-observe page
8. Validate expected state
```

For Selenium:

```java
try {
    element.click();
} catch (ElementClickInterceptedException e) {
    scrollIntoView(element);
    if (receivesClick(element)) {
        element.click();
    } else {
        actions.moveToElement(element).click().perform();
    }
}
```

For Playwright:

```javascript
await locator.scrollIntoViewIfNeeded();
await locator.click();
await expect(expectedElement).toBeVisible();
```

## 14. Where LLM/VLM should fit

Do **not** call LLM for every locator failure.

Use deterministic logic first.

```text
Deterministic layer:
    text match
    role match
    bbox match
    nearby label match
    DOM similarity
    locator stability
    browser validation

LLM/VLM layer:
    only if top candidates are close
    only if text changed semantically
    only if DOM structure changed heavily
    only if visual reasoning is needed
```

LLM/VLM should receive a compact prompt like:

| Trigger                  | Locator/action failure        | User/test goal              |
| Input                    | Old locator + failure context | High-level task             |
| Output                   | New locator/action target     | Next action/result          |
| Uses screenshot?         | Yes                           | Yes                         |
| Uses DOM?                | Yes                           | Yes                         |
| Uses accessibility tree? | Yes                           | Yes                         |
| Uses memory?             | Old locator history           | Workflow progress/history   |
| Uses scraping?           | To find replacement element   | To understand page state    |
| Uses planning?           | Limited                       | Strongly required           |
| Verification             | Did healed action work?       | Did workflow step progress? |

So you can build one common **Page Intelligence Layer**, then use it for both.

# 5. Recommended architecture

Build this as reusable layers:

```text
Browser Agent Platform
│
├── PageObserver
│   ├── Screenshot capture
│   ├── DOM snapshot
│   ├── Accessibility snapshot
│   ├── Visible text extraction
│   ├── Layout/bounding boxes
│   └── OCR/vision when needed
│
├── PageUnderstandingEngine
│   ├── Detect page type
│   ├── Extract forms/tables/buttons/errors
│   ├── Identify current workflow step
│   └── Build page state JSON
│
├── Planner
│   ├── Reads goal
│   ├── Reads current page state
│   ├── Decides next action
│   └── Produces action command
│
├── TargetResolver
│   ├── Finds correct element
│   ├── Uses DOM/accessibility/visual matching
│   ├── Generates locator
│   └── Scores candidate elements
│
├── ActionExecutor
│   ├── click
│   ├── type
│   ├── select
│   ├── scroll
│   ├── wait
│   └── extract
│
├── Validator
│   ├── Checks expected result
│   ├── Detects errors
│   ├── Confirms progress
│   └── Decides retry/fail/continue
│
├── HealingEngine
│   ├── Activates when target/action fails
│   ├── Finds replacement element
│   └── Updates locator memory
│
└── MemoryRepository
    ├── Workflow history
    ├── Successful locators
    ├── Page signatures
    ├── Past failures
    ├── Screenshot crops
    └── Healing decisions
```

# 6. Example: agent driving a browser workflow

Goal:

```text
Login to application and create a customer.
```

Agent loop:

```text
Step 1: Observe page
Page says: Username, Password, Login

Step 2: Plan
Need to enter username.

Step 3: Resolve target
Find input near label Username.

Step 4: Execute
Type username.

Step 5: Verify
Username field contains value.

Step 6: Observe again
Password field still empty.

Step 7: Plan
Type password.

Step 8: Execute
Type password.

Step 9: Plan
Click Login.

Step 10: Execute
Click Login button.

Step 11: Verify
Dashboard page loaded.

Step 12: Observe dashboard
Find Create Customer button.

Step 13: Continue workflow.
```

If “Create Customer” button changes to “Add Client”, the healing logic activates:

```text
Old expected: Create Customer
Visible now: Add Client
Same page area
Same role button
Same workflow intent
Click Add Client
```

So workflow execution and healing work together.

# 7. Agent action format

Your agent should not produce vague text like:

```text
Click the green button.
```

It should produce structured actions:

```json
{
  "stepId": "create_customer_001",
  "action": "click",
  "targetIntent": "open create customer form",
  "targetCandidateId": "btn-add-client",
  "preferredLocator": "button[data-testid='add-client']",
  "fallbackLocator": "//*[self::button or @role='button'][normalize-space()='Add Client']",
  "confidence": 0.92,
  "expectedResult": {
    "type": "modal_or_page",
    "visibleText": "Customer Details"
  }
}
```

Then executor performs the action and validator checks the expected result.

# 8. Page state JSON is very important

For agentic browser workflow, every observation should become structured page state:

```json
{
  "url": "/customers/new",
  "pageType": "customer_creation_form",
  "visibleTexts": [
    "Customer Name",
    "Email",
    "Phone",
    "Save",
    "Cancel"
  ],
  "forms": [
    {
      "name": "customerForm",
      "fields": [
        {
          "label": "Customer Name",
          "type": "text",
          "required": true,
          "filled": false
        },
        {
          "label": "Email",
          "type": "email",
          "required": true,
          "filled": false
        }
      ],
      "actions": ["Save", "Cancel"]
    }
  ],
  "errors": [],
  "modals": [],
  "tables": [],
  "nextPossibleActions": [
    "fill_customer_name",
    "fill_email",
    "click_save"
  ]
}
```

This page state is the real “understanding” layer.

# 9. Deterministic vs agentic control

For enterprise test automation, do not make the browser agent completely free-roaming.

Use this model:

```text
Deterministic workflow skeleton
+
Agentic perception and healing
+
Optional LLM reasoning for ambiguity
```

Example deterministic skeleton:

```text
1. Login
2. Navigate to Customers
3. Click Create Customer
4. Fill customer details
5. Save
6. Verify customer created
```

Agentic layer helps with:

```text
finding changed elements
handling changed labels
understanding modal/page variations
recovering from dropdown changes
scrolling to hidden fields
choosing correct button when UI shifts
extracting visible errors
```

This is safer than saying:

```text
Agent, create a customer somehow.
```

For your framework, better approach:

```text
Human/test defines business intent.
Agent handles UI uncertainty.
```

# 10. Four operating modes you can build

## Mode 1: Healing Mode

Used when locator fails.

```text
Find replacement element and continue.
```

## Mode 2: Workflow Mode

Used to complete a browser flow.

```text
Observe → plan → act → verify.
```

## Mode 3: Extraction Mode

Used to scrape structured data.

```text
Observe → locate data → extract → validate.
```

## Mode 4: Exploration Mode

Used to discover unknown application flow.

```text
Observe → map pages → identify navigation → build workflow graph.
```

For your current XPath-healer project, start with:

```text
Mode 1: Healing
+
Mode 2: Controlled workflow execution
```

Later add:

```text
Mode 3: Extraction
Mode 4: Exploration
```

# 11. Important distinction: scrape vs drive

The agent should scrape to understand, but not depend only on scraping.

```text
Scraping gives page information.
Planning decides what to do.
Target resolving finds the element.
Execution performs the browser action.
Validation confirms correctness.
Healing recovers from failure.
```

So scraping is one part of the agent, not the whole agent.

---

# 12. Final answer

Yes, the same principle works for both:

```text
Agentic healing
+
Agentic browser workflow execution
+
Structured scraping
+
Visual reasoning
+
DOM-based action
```

But the final design should be:

```text
Use screenshot/OCR/vision as the eyes.
Use DOM/accessibility as the action truth.
Use page-state scraping as the understanding layer.
Use planner/state machine as the workflow brain.
Use candidate scoring as the target selector.
Use browser validation as the final judge.
Use healing as the recovery mechanism.
```

In one line:

> **The browser agent should scrape the page to understand it, reason over the workflow state to decide the next step, use DOM/accessibility to act, and use the healing engine whenever the expected element or flow changes.**
